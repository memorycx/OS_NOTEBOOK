# 第六讲：进程的地址空间（Process Address Space）

## 一、本节课学习目标

学习本节课后，应当能够：

1. 理解什么是进程地址空间，以及为什么每个进程需要独立的地址空间。
2. 理解代码、数据、堆、栈在进程地址空间中的组织方式。
3. 理解程序从可执行文件加载到进程地址空间的过程。
4. 掌握 `mmap()`、`munmap()`、`mprotect()` 等内存管理 API 的基本作用。
5. 理解虚拟内存、MMU 与操作系统之间的关系。
6. 理解如何通过操作系统提供的机制访问、调试和修改其他进程的内存。
7. 理解内存修改工具（如游戏修改器）背后的基本原理。

## 二、进程管理 API 回顾

在正式学习地址空间之前，先回顾三个重要的进程管理 API：

- `fork()`
- `execve()`
- `_exit()`

它们分别对应进程状态的复制、重置和删除。

### 2.1 fork()：创建子进程

`fork()` 用于创建一个新的子进程。

调用 `fork()` 后，操作系统会创建一个与父进程具有相似初始执行状态的子进程。

```c
pid_t pid = fork();

if (pid == -1) {
    // 创建失败
    perror("fork");
} else if (pid == 0) {
    // 子进程
    printf("I am child process\n");
} else {
    // 父进程
    printf("I am parent process\n");
}
```

#### fork() 的返回值

| 返回值 | 含义 |
| --- | --- |
| -1 | 创建进程失败 |
| 0 | 当前执行的是子进程 |
| 正整数 | 当前执行的是父进程，返回值为子进程 PID |

#### fork() 的重要特点

从程序的角度来看，`fork()` 创建的子进程拥有独立的地址空间。

父子进程最初的内存内容相同，但后续修改互不影响。

现代操作系统通常使用 Copy-on-Write（写时复制）优化：

1. 创建子进程时，不立即复制全部物理内存。
2. 父子进程暂时共享相同的物理内存页面。
3. 当其中一个进程尝试修改页面时，操作系统才复制对应页面。
4. 修改只影响执行写操作的进程。

### 2.2 execve()：加载并执行新程序

`execve()` 用于用一个新程序替换当前进程的程序映像。

```c
execve(path, argv, envp);
```

参数：

- `path`：可执行文件路径。
- `argv`：命令行参数数组。
- `envp`：环境变量数组。

例如：

```c
char *argv[] = {
    "hello",
    "world",
    NULL
};

execve("./program", argv, environ);
```

#### execve() 的重要特点

- 不会创建新的进程。
- 当前进程的 PID 通常保持不变。
- 原有程序映像被新程序映像替换。
- 原有代码、数据、堆、栈等用户空间内容被重新建立。
- 新程序从自己的入口开始执行。

可以把 `execve()` 理解为：

> [!important] 核心理解
> 保留进程身份，替换进程正在执行的程序。

### 2.3 _exit()：终止进程

`_exit()` 用于直接终止当前进程。

```c
_exit(0);
```

参数通常表示退出状态：

- 0：正常退出。
- 非 0：通常表示出现错误。

与 C 标准库中的 `exit()` 不同，`_exit()` 不执行用户空间的标准 I/O 缓冲区刷新和 `atexit()` 注册函数。

操作系统负责回收进程退出后不再需要的资源。

### 2.4 waitpid()：等待子进程

父进程可以使用 `waitpid()` 等待子进程结束。

```c
int status;

waitpid(pid, &status, 0);
```

它可以用于：

- 等待指定子进程结束。
- 获取子进程退出状态。
- 避免子进程结束后长期处于僵尸进程状态。

#### 三个 API 的关系

| API | 核心作用 | 对进程的影响 |
| --- | --- | --- |
| fork() | 复制进程执行状态 | 创建子进程 |
| execve() | 替换程序映像 | 不创建新进程 |
| _exit() | 终止进程 | 当前进程退出 |
| waitpid() | 等待子进程 | 获取子进程状态 |

## 三、什么是进程的地址空间？

### 3.1 地址空间的定义

Address Space，即地址空间。

进程地址空间是操作系统为进程提供的一套独立的虚拟内存地址范围。

通常也称为：

**Virtual Address Space（虚拟地址空间）。**

每个进程都可以认为自己拥有一片独立、连续的内存空间。

例如：

```text
进程 A：

0x00000000
    |
    | 代码
    | 数据
    | 堆
    | ...
    | 栈
    |
0xFFFFFFFF


进程 B：

0x00000000
    |
    | 代码
    | 数据
    | 堆
    | ...
    | 栈
    |
0xFFFFFFFF
```

注意：这是概念示意图，并不代表现代操作系统实际使用的地址范围或布局。

#### 为什么需要地址空间？

主要有三个原因。

##### 1. 隔离与保护

不同进程的地址空间相互独立。

例如：

- 进程 A 无法直接访问进程 B 的普通私有内存。
- 进程 A 的非法内存访问不会正常地修改进程 B 的内存。
- 一个进程崩溃通常不会直接破坏其他进程的地址空间。

这可以提高系统的安全性和稳定性。

**扩展知识：[[GDB是如何进行代码调试]]**

##### 2. 便于内存管理

程序不需要关心实际物理内存是如何分配的。

程序只需要使用自己的虚拟地址。

操作系统和硬件负责将虚拟地址转换为物理地址。


##### 3. 支持有限的内存共享

虽然进程之间默认隔离，但操作系统也允许它们通过特定机制共享内存。

例如：

- 共享内存。
- 内存映射文件。
- 共享动态库。

因此，地址空间既提供隔离，也支持受控制的共享。

## 四、地址空间与指针

### 4.1 地址空间的本质

课程使用 CrazyOS 的结构帮助理解地址空间。

```c
#define MEM_SIZE   (1 << 20)
#define MEM_OFFSET 0x80000000u
#define STACK_TOP  (MEM_OFFSET + MEM_SIZE)

struct proc {
    struct CPUState cpu;
    uint8_t mem[MEM_SIZE];

    // OS-internal state
    // pid, buf, buf_len, ...
};
```

这里：

- `MEM_SIZE`：为进程模拟的内存大小，1 MiB。
- `MEM_OFFSET`：模拟地址空间的起始地址。
- `STACK_TOP`：模拟栈顶地址。
- `mem`：保存进程内存内容的数组。

对于 CrazyOS 来说，`mem` 就是模拟进程地址空间的主要部分。

它包含：

- 程序指令。
- 全局变量。
- 静态变量。
- 堆。
- 栈。

这些内容都位于同一份地址空间中。

### 4.2 指针可以访问地址空间

在 C 语言中，指针保存的是地址。

通过指针可以读取或修改对应地址上的内容。

```c
volatile char *ptr = input();

char value = *ptr;  // load

*ptr = 1;            // store
```

其中：

- `load`：从内存读取数据。
- `store`：向内存写入数据。

#### 为什么使用 volatile？

`volatile` 用来告诉编译器：

这个对象可能在程序正常执行流程之外发生变化，因此不能随意假设它的值一直不变。

例如：

```c
volatile int *ptr;
```

对于内存映射硬件寄存器、异步变化的共享状态等场景，`volatile` 具有重要意义。

但需要注意：

- `volatile` 不等于线程安全。
- `volatile` 不提供原子性。
- `volatile` 不负责内存访问权限检查。
- `volatile` 不会自动让非法地址变得可访问。

### 4.3 地址空间中的内容没有天然的类型

从计算机底层来看，内存本质上由一个个字节组成。

一个字节本身并不知道自己属于：

- 整数。
- 字符。
- 指令。
- 浮点数。
- 指针。

它的含义取决于程序如何解释这些字节。

例如：

```c
int x = 100;
char *p = (char *)&x;
```

这里 `p` 指向 `x` 的内存表示。

同一组字节，可以通过不同类型的指针进行不同方式的解释。

但具体解释必须遵守 C 语言的对象生命周期、对齐和别名规则等约束。

#### 关键理解

> [!important] 关键理解
> 内存本身只保存数据，类型和语义来自程序对数据的解释。

这也是为什么程序员可以通过指针观察代码、数据、栈等不同区域。

## 五、进程地址空间中的字节从哪里来？

这是本节课提出的核心问题之一：

一个进程中的每个字节是怎么产生的？谁决定它们放在哪里？

可以从三个方面理解。

### 5.1 CPU 的 ISA：决定字节如何被解释

ISA（Instruction Set Architecture，指令集架构）规定 CPU 如何执行指令。

例如：

- x86-64。
- ARM64。
- RISC-V。

ISA 决定：

- CPU 支持哪些指令。
- 指令如何编码。
- 寄存器的使用方式。
- 数据如何参与运算。
- CPU 如何访问内存。

因此，内存中的字节如果被当作指令执行，其含义由对应的指令集架构决定。

### 5.2 编译器与链接器：决定字节放在哪里

程序经过编译、汇编和链接，最终形成可执行文件。

可执行文件通常包含不同的段（Section）。

常见段：

| 段         | 主要内容                |
| --------- | ------------------- |
| `.text`   | 程序指令                |
| `.rodata` | 只读数据，例如字符串常量        |
| `.data`   | 已初始化的全局变量和静态变量      |
| `.bss`    | 未初始化或零初始化的全局变量和静态变量 |

例如：

```c
int global_a = 100;

int global_b;

const char *message = "hello";

int main() {
    int local = 10;
    return 0;
}
```

其中：

- `main()` 对应的机器指令通常位于 `.text`。
- `"hello"` 对应的字符串常量通常位于只读数据区域。
- `global_a` 通常位于 `.data`。
- `global_b` 通常位于 `.bss`。
- `local` 通常位于函数调用使用的栈空间。

注意：这是常见布局，实际位置还受到编译器、链接器、ABI 和优化方式影响。

### 5.3 操作系统加载器与 ABI：决定初始内存状态

程序编译完成后，还需要操作系统将它加载到进程地址空间中。

ABI（Application Binary Interface，应用程序二进制接口）规定程序与操作系统、运行环境之间的一系列二进制层面约定。

程序执行 `execve()` 后，操作系统加载器主要完成以下工作：

1. 读取可执行文件。
2. 解析可执行文件格式。
3. 将需要加载的程序段映射到进程地址空间。
4. 根据段的要求设置访问权限。
5. 将 `.bss` 对应的内存初始化为零。
6. 建立初始 CPU 状态。
7. 设置程序计数器 PC。
8. 设置栈指针 SP。
9. 在初始栈中准备参数和环境变量等内容。

#### 初始栈的内容

在常见的 System V ABI 环境中，初始栈涉及：

- `argc`：命令行参数数量。
- `argv`：命令行参数数组。
- `envp`：环境变量数组。
- `auxv`：辅助向量。

其中参数字符串和环境变量字符串通常也会放在初始用户栈附近。

#### PT_LOAD 段

ELF 可执行文件包含 Program Header。

其中 `PT_LOAD` 用于描述需要加载到进程地址空间的段。

每个加载段会描述：

- 文件中的偏移。
- 预期虚拟地址。
- 文件中的数据大小。
- 内存中的大小。
- 访问权限。

常见权限：

| 权限 | 含义 |
| --- | --- |
| R | Read，读取 |
| W | Write，写入 |
| X | Execute，执行 |

例如：

```text
.text   -> R-X
.rodata -> R--
.data   -> RW-
.bss    -> RW-
```

这里仅为常见示意，具体权限取决于 ELF 文件和加载器设置。

#### 总结：谁决定了内存中的字节？

| 层次 | 负责的事情 |
| --- | --- |
| ISA | 决定机器指令如何解释和执行 |
| 编译器、汇编器 | 生成程序的机器代码和数据 |
| 链接器 | 组织程序段和地址布局 |
| ELF 文件格式 | 描述程序需要如何加载 |
| ABI | 规定程序与运行环境之间的约定 |
| OS 加载器 | 建立进程初始地址空间 |
| MMU | 在运行过程中完成虚拟地址到物理地址的转换和访问控制 |

## 六、MMU：操作系统给进程戴上的 VR 眼镜

### 6.1 什么是 MMU？

MMU（Memory Management Unit，内存管理单元）是 CPU 系统中的内存管理硬件。

它负责虚拟地址到物理地址的转换，以及相关的访问权限检查。

可以把虚拟地址理解为程序看到的地址，把物理地址理解为实际访问的内存地址。

例如：

```text
进程 A：

虚拟地址 0x1000
        |
        v
       MMU
        |
        v
物理地址 0x5000


进程 B：

虚拟地址 0x1000
        |
        v
       MMU
        |
        v
物理地址 0x9000
```

两个进程可以使用相同的虚拟地址，但最终映射到不同的物理内存。

这就是虚拟内存隔离的基础之一。

### 6.2 页表

操作系统通过页表等数据结构管理虚拟地址和物理地址之间的映射关系。

虚拟内存通常按页（Page）进行管理。

常见页面大小为 4 KiB，但也支持其他页面大小。

一个简化的转换过程：

```text
CPU 发出虚拟地址
        |
        v
      MMU
        |
        v
    查询 TLB
        |
   +----+----+
   |         |
 命中       未命中
   |         |
   |       查询页表
   |         |
   +----+----+
        |
        v
   得到物理地址
        |
        v
    访问物理内存
```

TLB（Translation Lookaside Buffer）是用于缓存地址转换结果的高速缓存。

如果页表中不存在有效映射，或者访问违反权限要求，可能触发异常。

#### 缺页异常（Page Fault）

当进程访问的虚拟地址没有对应的有效物理页面时，CPU 可能触发缺页异常。

操作系统接管后，根据具体情况：

- 分配新的物理页面。
- 从文件中读取页面。
- 处理写时复制。
- 或者判定访问非法，终止进程或向进程发送信号。

> [!warning] 注意
> 缺页异常不一定意味着程序出错。它也可能是操作系统正常管理虚拟内存的机制。

## 七、地址空间管理 API

了解地址空间后，一个自然的问题是：

如果程序需要更多内存，应该向谁申请？

答案是操作系统。

操作系统提供系统调用来管理进程地址空间。

### 7.1 brk() 和 sbrk()

在传统 UNIX 系统中，可以使用 `brk()` 和 `sbrk()` 调整进程的数据段末尾位置。

这个位置称为 Program Break。

```text
低地址
  |
  | .text
  | .rodata
  | .data
  | .bss
  |
  | Program Break
  |      ↑
  |      | 堆增长方向
  |
  |      Heap
  |
高地址
```

简单理解：

- `brk()`：设置 program break。
- `sbrk()`：按照指定增量调整 program break。

现代程序通常通过 `malloc()` 等接口管理动态内存。

`malloc()` 的底层实现可以根据需求使用 `brk()`、`mmap()` 等机制。

### 7.2 mmap()：内存映射系统调用

`mmap()` 是 Linux 中非常重要的内存管理接口。

它可以在进程地址空间中建立一段映射区域。

函数原型：

```c
void *mmap(
    void *addr,
    size_t length,
    int prot,
    int flags,
    int fd,
    off_t offset
);
```

参数说明：

| 参数 | 作用 |
| --- | --- |
| addr | 建议映射的虚拟地址 |
| length | 映射长度 |
| prot | 内存访问权限 |
| flags | 映射类型和属性 |
| fd | 文件描述符 |
| offset | 文件映射偏移量 |

#### prot：内存访问权限

常见选项：

| 宏 | 含义 |
| --- | --- |
| PROT_READ | 可读 |
| PROT_WRITE | 可写 |
| PROT_EXEC | 可执行 |
| PROT_NONE | 不允许访问 |

可以使用位运算组合权限：

```c
PROT_READ | PROT_WRITE
```

#### flags：映射类型

常见选项：

| 宏 | 含义 |
| --- | --- |
| MAP_PRIVATE | 私有映射 |
| MAP_SHARED | 共享映射 |
| MAP_ANONYMOUS | 匿名映射，不依赖普通文件内容 |

#### mmap() 的两种常见用途

##### 1. 匿名内存映射

申请一段不直接对应普通文件内容的内存。

```c
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>

int main() {
    size_t size = 4096;

    void *ptr = mmap(
        NULL,
        size,
        PROT_READ | PROT_WRITE,
        MAP_PRIVATE | MAP_ANONYMOUS,
        -1,
        0
    );

    if (ptr == MAP_FAILED) {
        perror("mmap");
        return 1;
    }

    int *data = (int *)ptr;

    data[0] = 100;

    printf("%d\n", data[0]);

    munmap(ptr, size);

    return 0;
}
```

执行过程：

1. 调用 `mmap()`。
2. 操作系统建立虚拟内存映射。
3. 返回映射区域的起始虚拟地址。
4. 程序通过指针访问内存。
5. 使用 `munmap()` 解除映射。

注意：成功返回 `mmap()` 并不代表所有对应物理页面都已经分配。

##### 2. 文件映射

可以将文件内容映射到进程地址空间。

例如：

```c
void *ptr = mmap(
    NULL,
    length,
    PROT_READ,
    MAP_PRIVATE,
    fd,
    0
);
```

建立映射后，程序可以像访问内存一样读取文件内容。

不必通过传统的 `read()` 一次次读取数据。

这种机制对于处理大型文件非常有用。

### 7.3 munmap()：解除内存映射

函数原型：

```c
int munmap(void *addr, size_t length);
```

作用：

解除指定地址范围的内存映射。

例如：

```c
munmap(ptr, size);
```

使用后，原映射区域不再属于该进程的有效映射。

如果之后继续访问该区域，可能产生非法内存访问。

### 7.4 mprotect()：修改内存访问权限

函数原型：

```c
int mprotect(
    void *addr,
    size_t len,
    int prot
);
```

作用：

修改一段已经映射的内存区域的访问权限。

例如：

```c
mprotect(
    ptr,
    size,
    PROT_READ
);
```

将对应内存区域设置为只读。

常见用途：

- 内存保护。
- JIT（Just-in-Time）动态代码生成。
- 调试器。
- 安全检测工具。

#### JIT 与 mprotect()

JIT 技术可以在程序运行时生成机器代码。

一种常见设计是：

1. 申请一段可读写内存。
2. 在其中生成机器指令。
3. 将内存权限修改为可读、可执行。
4. 执行生成的代码。

这种方式可以减少内存区域同时可写、可执行带来的安全风险。

## 八、为什么 mmap() 如此重要？

课程强调：

> [!important] 核心观点
> 很多与内存相关的功能，底层都可以通过 mmap() 实现。

### 8.1 malloc() 与 mmap()

C 语言中的：

```c
void *ptr = malloc(1024);
```

并不意味着每次调用 `malloc()` 都会直接执行一次系统调用。

一般来说：

1. 用户空间内存分配器维护自己的内存池。
2. 当内存池空间不足时，向操作系统申请更大的内存区域。
3. 操作系统可以使用 `brk()` 或 `mmap()` 等方式提供内存。
4. 分配器再把较小的内存块分配给程序。

因此：

```text
malloc()
   |
   v
用户空间内存分配器
   |
   v
brk() / mmap()
   |
   v
操作系统
   |
   v
虚拟内存管理
```

### 8.2 为什么 mmap() 可以快速申请大量内存？

一个重要原因是：虚拟地址空间的建立不一定要求立即分配所有物理内存。

例如：

```c
mmap(
    NULL,
    1ULL << 30,
    PROT_READ | PROT_WRITE,
    MAP_PRIVATE | MAP_ANONYMOUS,
    -1,
    0
);
```

这里申请了一个 1 GiB 的虚拟内存区域。

在支持按需分配的系统中：

- 映射建立时，不一定分配全部物理页面。
- 第一次访问某个页面时，可能触发缺页异常。
- 操作系统再根据需要分配实际物理页面。

这称为 Demand Paging（按需分页）。

因此：

> [!important] 核心结论
> 申请虚拟内存不等于立即占用同等大小的物理内存。

不过，实际行为还受内核策略、内存提交限制和资源约束影响。

### 8.3 内存映射 I/O

Memory-mapped I/O 可以将设备或文件映射到进程地址空间。

例如，Linux 中某些设备接口可以通过映射方式访问设备寄存器。

程序通过读写特定内存地址来完成设备交互。

这也是 Everything is a file 思想在操作系统中的一种延伸。

### 8.4 进程间共享内存

进程间可以使用共享内存进行通信。

例如：

```c
shm_open()
```

它可以创建或打开一个 POSIX 共享内存对象。

随后使用 `mmap()` 将该对象映射到进程地址空间。

```text
进程 A                  进程 B
   |                       |
   | mmap                  | mmap
   |                       |
   v                       v
虚拟地址 A              虚拟地址 B
   |                       |
   +-----------+-----------+
               |
               v
          共享物理页面
```

两个进程可以通过共享区域交换数据。

需要注意，共享内存只解决了数据共享问题，并不自动解决并发访问问题。

通常还需要互斥锁、信号量或原子操作等同步机制。

## 九、探索与修改其他进程的地址空间

前面学习了每个进程都有独立的地址空间。

但这并不意味着一个进程永远无法访问其他进程的内存。

操作系统可以提供一些受权限控制的机制，让调试器等工具访问其他进程的地址空间。

### 9.1 调试器如何访问其他进程？

例如 GDB。

调试器可以：

- 查看寄存器。
- 查看内存内容。
- 设置断点。
- 单步执行。
- 修改变量。
- 修改程序执行状态。

这些功能需要操作系统提供底层支持。

在 Linux 中，常见机制包括：

- `ptrace()`。
- `/proc` 文件系统。
- `process_vm_readv()`。
- `process_vm_writev()`。

这些接口都受到权限和安全策略约束。

#### ptrace()

`ptrace()` 是 Linux 提供的进程跟踪和调试接口。

调试器可以使用它控制目标进程的执行，并读取或修改部分进程状态。

例如：

```text
GDB
 |
 v
ptrace()
 |
 v
操作系统
 |
 v
目标进程
```

这也是为什么 GDB 可以在一定权限范围内检查其他进程的内存。

### 9.2 /proc 文件系统

Linux 提供 `/proc` 伪文件系统。

其中：

```text
/proc/<pid>/
```

可以查看指定进程的相关信息。

例如：

```text
/proc/1234/maps
```

可以查看 PID 为 1234 的进程当前的内存映射区域。

常见内容包括：

- 地址范围。
- 访问权限。
- 文件偏移。
- 映射设备。
- inode。
- 映射文件路径。

例如：

```text
7f0000000000-7f0000020000 rw-p 00000000 00:00 0
```

可以将它理解为一个虚拟地址范围及其相关映射属性。

### 9.3 process_vm_readv() 和 process_vm_writev()

Linux 还提供了跨进程内存读写接口。

```c
process_vm_readv()
```

用于读取其他进程的内存。

```c
process_vm_writev()
```

用于向其他进程写入内存。

它们适用于调试器、分析工具等需要跨进程访问内存的场景。

访问仍然受到系统权限和目标进程状态等条件限制。

## 十、案例：游戏修改器的工作原理

本节课使用游戏修改器作为案例，帮助理解地址空间的实际应用。

### 10.1 游戏中的数据存在哪里？

假设一个游戏中有经验值：

```c
int exp = 4950;
```

游戏运行时，这个变量对应的数据会存储在进程地址空间中的某个位置。

如果游戏击败怪物后经验增加：

```text
初始经验：4950

击败怪物：

经验值：5100
```

那么我们就可以尝试在进程内存中寻找这个变化。

### 10.2 内存扫描的基本原理

假设我们不知道经验值存储在哪个地址。

可以采用以下思路：

1. 扫描游戏进程的内存。
2. 搜索值为 4950 的候选位置。
3. 在游戏中击败一个怪物。
4. 再次扫描，筛选值为 5100 的位置。
5. 重复观察和筛选。
6. 最终找到可能存储经验值的地址。

例如：

```text
第一次扫描：

候选地址 A = 4950
候选地址 B = 4950
候选地址 C = 4950
候选地址 D = 4950


经验增加后：

候选地址 A = 4950
候选地址 B = 5100
候选地址 C = 4950
候选地址 D = 4950
```

此时 B 就是一个值得进一步验证的候选地址。

找到正确地址后，可以尝试修改其中的数据。

例如：

```c
*ptr = 1000000;
```

这就是早期游戏修改器的一种基本原理。

### 10.3 Game Genie 的工作原理

课程介绍了 Game Genie。

它与现代内存扫描工具有所不同。

Game Genie 的核心思想是使用查找表（LUT，Look-up Table）修改特定内存读取结果。

可以理解为：

```text
CPU 请求读取地址 a
        |
        v
检查查找表 LUT
        |
        v
原本应该读取 x
        |
        v
替换为 y
        |
        v
CPU 得到修改后的结果
```

例如：

```text
原始结果：100

替换结果：999999
```

这样就能改变游戏读取到的数据。

Game Genie 通过卡带等硬件介入游戏机的数据访问过程，在当时实现了类似内存修改的效果。

### 10.4 为什么内存扫描并不是万能的？

课程给出了一个重要问题：

有些游戏通过扫描数值无法直接找到想修改的内容。

例如：

```c
state_new = new State(state);

state_new.update(exp);

state = state_new;
```

这里的程序并不一定直接修改原有的经验值存储位置，而可能创建新对象并更新状态。

因此：

- 原来的地址可能已经失效。
- 新对象可能位于其他地址。
- 内存中可能存在多个相同数值。
- 数据可能经过加密、编码或压缩。
- 经验值可能由多个变量共同计算得到。

这说明：

> [!important] 核心结论
> 仅仅知道内存中的数值还不够，还需要理解程序的语义。

### 10.5 从数据扫描到程序语义分析

想要制作更通用的游戏辅助工具，需要理解：

- 什么数据代表经验值。
- 什么数据代表金钱。
- 什么数据代表生命值。
- 数据是如何更新的。
- 游戏使用了哪些函数和系统调用。

这已经涉及程序逆向分析和调试技术。

例如，变速齿轮一类工具可以通过分析和调整与时间有关的系统调用行为，实现程序运行速度变化。

课程还将汉诺塔作为案例，说明程序的语义不仅是数据，还包括执行顺序和副作用。

## 十一、C/C++ 函数调用与副作用

课程使用汉诺塔和 Fibonacci 递归对比，说明函数调用顺序的重要性。

### 11.1 数学函数与程序函数的区别

在数学中：

$$
f(a)+f(b)=f(b)+f(a)
$$

只要函数结果不变，两个计算的先后顺序通常不影响最终结果。

但是在 C/C++ 中，函数可能产生副作用（Side Effect）。

例如：

```c
void move(int from, int to) {
    printf("Move from %d to %d\n", from, to);
}
```

这个函数除了执行计算，还会向屏幕输出内容。

因此，调用顺序会影响最终输出。

### 11.2 Fibonacci 递归

```c
int fib(int n) {
    if (n <= 1) {
        return n;
    }

    int x = fib(n - 1);
    int y = fib(n - 2);

    return x + y;
}
```

这里两个递归调用的结果只是用于计算最终数值。

在没有其他可观察副作用的情况下，计算顺序通常不会改变最终数学结果。

但下面的表达式：

```c
return fib(n - 1) + fib(n - 2);
```

在 C 语言中也不保证左右操作数按照从左到右的顺序求值。

### 11.3 汉诺塔递归

汉诺塔算法：

```c
void hanoi(int n, char A, char B, char C) {
    if (n == 1) {
        printf("%c -> %c\n", A, C);
        return;
    }

    hanoi(n - 1, A, C, B);

    printf("%c -> %c\n", A, C);

    hanoi(n - 1, B, A, C);
}
```

汉诺塔的移动操作有严格的先后顺序。

原因是：

- 必须先将上面的 n-1 个盘子移走。
- 才能移动最底下的盘子。
- 最后再把 n-1 个盘子移动到目标柱子。

如果随意交换递归调用顺序，就会破坏算法的正确性。

#### 本节核心

程序函数不仅仅是数学意义上的输入与输出。

程序还可能：

- 修改全局变量。
- 修改共享状态。
- 读写文件。
- 输出信息。
- 调用系统 API。

这些行为都属于副作用。

因此，程序的执行顺序可能直接影响最终结果。

## 十三、本节课知识总结

### 13.1 核心知识点

| 知识点 | 核心内容 |
| --- | --- |
| 进程地址空间 | 每个进程拥有独立的虚拟地址空间 |
| 虚拟内存 | 为进程提供独立的地址视图 |
| MMU | 完成地址转换和访问权限检查 |
| 页表 | 管理虚拟地址到物理地址的映射 |
| ELF | 描述可执行文件的组织和加载信息 |
| ABI | 规定程序与运行环境之间的二进制接口约定 |
| PT_LOAD | 描述需要加载到内存中的程序段 |
| brk/sbrk | 调整传统进程数据段末尾 |
| mmap | 建立内存映射 |
| munmap | 解除内存映射 |
| mprotect | 修改内存访问权限 |
| ptrace | 提供进程跟踪和调试能力 |
| process_vm_readv | 跨进程读取内存 |
| process_vm_writev | 跨进程写入内存 |
| 共享内存 | 允许多个进程访问同一片共享内存 |

### 13.2 最重要的三条结论

#### 结论一：每个进程都有独立的地址空间

操作系统通过虚拟内存机制为每个进程建立独立的地址空间，实现隔离和保护。

#### 结论二：mmap 是现代内存管理的重要基础

`mmap()` 不仅可以申请匿名内存，还可以映射文件、实现共享内存，并配合 `mprotect()` 实现灵活的内存权限管理。

#### 结论三：进程之间并不是完全无法访问彼此的内存

在操作系统提供的权限控制机制下，调试器和分析工具可以访问、检查甚至修改其他进程的地址空间。

### 实践一：观察程序中的不同内存区域

编写一个 C 程序，定义：

- 全局变量。
- 静态变量。
- 局部变量。
- 动态分配变量。
- 字符串常量。
- 函数。

打印它们的地址：

```c
#include <stdio.h>
#include <stdlib.h>

int global_var = 100;
int global_bss;

const char *str = "Hello OS";

void test() {
    printf("Function address: %p\n", (void *)test);
}

int main() {
    static int static_var = 200;

    int local_var = 300;

    int *heap_var = malloc(sizeof(int));

    if (heap_var == NULL) {
        return 1;
    }

    *heap_var = 400;

    printf("Global:   %p\n", (void *)&global_var);
    printf("BSS:      %p\n", (void *)&global_bss);
    printf("Static:   %p\n", (void *)&static_var);
    printf("Local:    %p\n", (void *)&local_var);
    printf("Heap:     %p\n", (void *)heap_var);
    printf("String:   %p\n", (void *)str);

    test();

    free(heap_var);

    return 0;
}
```

观察不同对象的地址，并思考：

1. 为什么全局变量和局部变量的地址通常不同？
2. 为什么堆和栈通常位于不同的地址区域？
3. 为什么函数地址可以通过函数指针等方式观察？
4. 多次运行程序，为什么地址可能发生变化？
